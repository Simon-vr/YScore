# Preface: Some of My Thoughts

## Why I Built This Project

In April 2026, in the second semester of my third year, I grew increasingly weary of AI. For many course assignments — vision, multimodal, machine learning, all kinds of generative models — all you have to do now is throw the PDF the instructor handed out into Cursor, and without even truly running or debugging anything, you get an answer that looks finished. The code certainly runs, and the lab report certainly gets written, but it became harder and harder for me to feel that this was something I had made. And after three years of studying computer science, I still had not had a single project I did purely because I loved it and actually finished from beginning to end. They were either assignments, or abandoned halfway, or code riddled with traces of AI. They might prove that I passed some courses, but it was hard for them to prove that I had personally created anything. I am not proud of them.

So I began to wonder: could there be a project where I chose the direction entirely by my own interest, defined the problem myself, decided for myself how far to take it, and then spent enough time to truly finish it? Not for a course grade, not for a line on my résumé, not even to prove that some technology is fashionable — but simply to recover something that coding once gave me. A very raw kind of humanism: one person facing an empty file, starting from nothing, bit by bit turning what is in their mind into a machine that actually exists; and when it finally runs, being able to say without a shred of doubt: I made this.

Then I recalled two earlier labs. In my second year, for the computer organization lab, I once wrote a MIPS processor in Verilog; but at the time I was working with an advisor on dexterous-hand grasping, so I did not put much time or energy into it, and many parts were really just done to get by. MIPS, moreover, has gradually left the mainstream ISA stage, so it was hard for me to see that project as a truly continuous piece of engineering. Later, in the operating systems lab, I built an OS on QEMU and an IA32 emulator using C++ and x86 assembly. That project really was done by hand, with some AI assistance, but the framework, startup code, and a great deal of infrastructure were already prepared; what we actually did was fill in the key parts such as task scheduling and memory allocation. Neither project was easy at the time, and low-level development has a particular kind of difficulty: many problems cannot be solved just by reading code. Verilog simulation waveforms, exact timing, memory maps, the ABI, the boot process, hardware resource limits — unlike ordinary software bugs, you cannot simply hand these to an AI and get an answer. And so I suddenly realized: if I really wanted to build a project that could prove something about me, why not combine these two projects — write a processor from scratch myself, and then build a software system that genuinely runs on top of that processor, also from scratch? And so this project began.

## Who This Project Is For, and What You Can Learn

At heart, this project is not a tutorial on implementing a CPU from scratch; it is a route that truly strings the computer-systems courses together. If you stay only at the course level, subjects like computer organization, operating systems, and compiler principles often remain disconnected from one another — but once you actually build a processor, they suddenly connect. A single line of C eventually becomes a group of RV32I instructions entering your fetch, decode, execute, and write-back stages; a single `lw` eventually becomes one bus access; a timer raises an interrupt, the CPU saves `mepc` and `mcause` and jumps into the exception handler, and the operating system then uses that interrupt to drive task scheduling; finally the UART sends the program's output to a terminal. The whole process is no longer a block diagram in a textbook, but a chain that actually runs. This makes the project especially suitable for people who have already taken these courses yet still feel that they only ever mattered for exams.

You will also learn things that are hard to appreciate in a classroom: why a seemingly ordinary `sw` exposes a completely different problem once it uses a negative-offset address generated by the compiler; why the linker script, startup code, and ABI are not mere software details but prerequisites for the processor to run C programs at all; why exceptions must be synchronous; and why interrupts must not casually cut into a program halfway through. And, most importantly, the truly difficult part of a system is often not implementing a single module in isolation, but connecting all the modules in the right way. This project does not chase a feature-bloated processor; its goals are relatively restrained: RV32I, Zicsr, exceptions and interrupts, AXI4-Lite, on-chip RAM, CLINT, UART, GPIO — and on top of that, complete C programs and a minimal real-time system. The hardware scale is not large, but I wanted the system as a whole to be complete.

## Project Timeline

- **April**: first wrote an RV32I single-cycle processor.
- **May**: the single-cycle version quickly proved to be only a starting point. Once I seriously considered a synthesizable, FPGA-ready implementation, a large number of practical problems began to appear in what had seemed a simple design, so I carried out a substantial refactor — changing it to a four-stage multi-cycle structure and later to five stages — while trying to keep the interfaces and datapath able to evolve into a pipeline later.
- **June**: final exams took up most of my energy, so work paused. I reviewed compiler principles and parallel computing, and realized that much of what I had learned reappears in completely different forms once you build a real system.
- **July**: began adding exceptions, CSR, interrupts, and the bus. I implemented Zicsr, ecall, ebreak, mret, exception handling, and timer interrupts one after another, and started connecting the CPU to peripherals. The bus was a clear watershed; this stage was also one of the most painful yet most rewarding parts of debugging in the whole project.
- **August**: once the hardware finally began to look like a real computer, the next step was making it run real software — first startup, C programs, the ABI, and memory layout, then the UART driver, shell, and GPIO, and finally a minimal real-time system, including tasks, context switching, scheduling, yield, delay, blocking and wake-up, and CLINT-based timer ticks, until multiple tasks were actually running on this self-designed processor.
- **September**: organized the test system, completed the engineering documentation, and ran long-duration stress tests on the FPGA.

## After It All Ended

So — if this project began as an attempt to prove that, in the face of AI, some small, meager human strength still remains, did I succeed? No. In fact, looking back on it all, I feel more like Don Quixote swinging his sword at windmills. Because the conclusion I ultimately reached is precisely not that humans can defeat AI, but that we should embrace it. Without AI's help, this project could never have been completed in about three months, and on an intermittent schedule at that. Much of the time, AI wrote code for me, explained protocols, checked my reasoning, and found references; it drove the cost of implementation itself down sharply. Yet at the same time, I also saw more clearly than before where AI's boundaries lie. I increasingly feel that what is truly hard for AI is not mainly designing something, nor exactly implementing a design, but rather the two ends of the smile curve: requirements, and verification.

When I say "I want to build a CPU", that means almost nothing. What ISA will I use? Which extensions should be supported? How many stages? Where does memory live? What bus does the system use? What exceptions are needed? How far does the software need to run? How much RAM is there? If these questions are not clear, AI cannot truly complete the design for you — because AI can propose an implementation very efficiently, but it does not know whether that implementation is what I want. The reason this project kept being refactored at the start is essentially that the requirements kept being redefined. From implementing an RV32I CPU, to implementing a synthesizable, board-ready multi-cycle RV32I CPU, to implementing an SoC with exceptions, interrupts, AXI, UART, and CLINT that can run C and a real-time system — these are in fact completely different requirements. And the further I went, the more specific the requirements became. The final system, for instance, had some limits that looked utterly trivial: instruction and data memory combined had to be under 50KB. That constraint directly affects what the RTOS should and should not implement. If a general-purpose message-queue system swallowed a large amount of space, I had to ask whether it was really worth existing; in the end, rather than implement a shrunken FreeRTOS, it was better to spend the limited resources on a multi-tasking application that actually runs. Requirements determine design, and requirements themselves are exactly what is hard to generate automatically.

Another thing that left a deep impression on me was verification. AI can help me write Verilog, but it cannot directly see the waveforms inside my FPGA simulator, nor know out of thin air why a register became a certain value on a certain clock edge. It can tell me that a piece of logic looks fine. But the real problem may be hiding somewhere completely different. This actually happened in the project: the disassembly was perfectly correct, the CPU's ALU results were correct, and a given instruction passed when tested in isolation — yet running a real C program still went off the rails. The problem turned out not to be the CPU at all, but the ELF-to-binary conversion and the memory layout. Or again: `sw` and `lw` passed completely in isolation, but the stack frames generated by the C compiler had a problem. Bugs like these are very hard to solve by reading code; in the end you have to go back to waveforms, traces, memory contents, register changes, and real hardware. People always tend to believe what they want to believe. This certainly does not mean that human checking is inherently more reliable than AI — humans make mistakes too, and many mistakes come precisely from confidence. But in many settings where the cost of verification is very high, verification is itself an independent skill. This is true of chip design, true of robotics, and true of any real-world system.

Now, in fact, I think the biggest impact of AI on computing is probably not the simple question of whether AI will write code in the future. The Verilog front end is not such a high barrier: as long as there is a good enough interface that lets AI actually obtain waveforms, simulation logs, and synthesis results, it can do a great deal of RTL design and debugging. Low-level software need not be such a high barrier either: with clear requirements, clear interfaces, clear hardware manuals, and sufficiently thorough tests, AI can likewise do a great deal of low-level work. Even computer architecture research is the same. Much of it ultimately forms a very simple loop: inside a controlled simulator, trade off multiple designs on performance, area, and power, and then search for a better design. As long as the requirements are clear, design automation itself may become easier and easier. The same goes for operators: what is truly hard may not be writing the program, but deciding what should be done and how to prove it was done correctly. This also means that some fields which today seem to depend heavily on coding ability may change very profoundly in the future, while requirements and verification may become increasingly important skills.

This is the first digital IC or computer architecture project I have done seriously, and judging by how things look now, it may well also be the last — though I very much hope it will not be. At the very least, this project let me reconfirm one thing: I do not dislike computers; I am simply increasingly unsatisfied with writing code only inside problems that others have already defined. Rather than training a model, I prefer to know why a machine can run; rather than getting an API to work, I prefer to know what the data actually goes through; rather than completing an assignment, I prefer to define a goal for myself and then carry it all the way through. As for whether I will continue with CPUs, digital ICs, or computer architecture in the future, I do not know. The author may later put more energy into robot control, where the real world constantly provides feedback, the automation loop is longer, the cost of verification is higher, and the system no longer faces just a controlled simulator but sensors, dynamics, the environment, and the physical world itself. Perhaps there will be greater challenges there, and more things worth automating and exploring. But no matter where I go from here, this project has at least accomplished one thing: it has finally become a project that truly belongs to me. From the first RV32I instruction to the moment when, on the FPGA, the UART outputs, the GPIO blinks, the timer interrupts, the tasks are scheduled, and the application finally runs — there was no ready-made "done" button in between; I could only build it layer by layer, verify it bit by bit, and then, finally, make it run.
