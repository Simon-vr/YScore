# 前言：我的一些想法

## 为什么要做这个项目

2026年4月，大三下学期，我越来越对AI感到厌倦。很多课程作业，视觉、多模态、机器学习、各类生成模型，现在只需要把老师给的PDF丢给Cursor，甚至不需要真正运行和调试，就可以得到一个看起来完成了的答案。代码当然可以运行，实验报告当然可以写，但我越来越难从中获得一种这是我做出来的东西的感觉。而计算机已经学了三年，我却始终没有一个真正纯粹因为自己喜欢、并且最后完整做完的项目。要么是作业，要么是做到一半放弃，要么代码里充满了AI的痕迹。它们或许能证明我完成过一些课程，却很难证明我究竟亲手创造过什么。我并不为它们感到自豪。

于是我开始想，能不能有这样一个项目，完全按照自己的兴趣选择方向，自己定义问题，自己决定做到什么程度，然后花足够长的时间把它真正做完。不是为了课程成绩，不是为了简历上的一行经历，甚至也不是为了证明某一项技术有多么热门，只是想重新找回一些编码曾经带给我的东西。一种很原始的人文主义：一个人面对一个空白文件，从什么都没有开始，一点一点把脑海中的东西变成真实存在的机器；当它最终运行起来的时候，我能够毫不怀疑地说，这是我做出来的。

这时我又回忆起之前的两个实验。大二做组成原理实验的时候，我曾经用Verilog写过一个MIPS处理器，但那个时候正在跟老师做灵巧手抓取，投入的时间和精力并不多，所以很多部分其实只是应付着完成，更何况MIPS已经逐渐退出主流ISA的舞台，我很难把那个项目看成一项真正有延续性的工程。后来做操作系统实验，在QEMU和IA32模拟器上，用C++和x86汇编完成操作系统，那个项目确实是我自己手工完成的，AI也提供过辅助，但框架、启动代码和大量基础设施早就准备好了，我们真正做的只是把任务调度、内存分配之类的关键部分补进去。这些项目当时都不算轻松，尤其是底层开发有一种特殊的困难：很多问题没有办法靠看代码解决，Verilog仿真的波形、具体的时序、内存映射、ABI、启动过程、硬件资源限制，这些东西不像普通的软件bug一样，丢给AI就可以直接得到答案。于是我突然意识到，如果我真的想做一个能够证明自己的项目，为什么不把这两个项目结合起来，自己从零开始写一个处理器，再在这个处理器上从零开始做一个真正运行的软件系统。于是这个项目就开始了。

## 本项目适合谁？能学到什么

这个项目本质上不是一个从零实现CPU的教程，而是一条把计算机系统课程真正串起来的路线。如果只停留在课程层面，组成原理、操作系统、编译原理这些知识往往是互相割裂的，但当你真正做一个处理器以后，它们会突然连接起来。一条C语言语句最终会变成一组RV32I指令，进入你的取指、译码、执行和写回；一条lw最终变成一次总线访问；定时器产生中断，CPU保存mepc和mcause，进入异常处理程序，操作系统再利用这个中断去驱动任务调度；最终UART把程序运行的结果送到终端。整个过程不再是一张课本里的框图，而是一条真正运行起来的链路。这个项目也因此非常适合那些已经学过这些课程，却始终觉得它们只是在考试时会用的人。

它也会学到一些课堂上很难体会到的东西，比如为什么一个看起来正常的sw，换成编译器生成的负偏移地址之后却暴露出完全不同的问题；为什么linker script、startup code和ABI并不是软件的细节，而是处理器能够运行C程序的必要条件；为什么异常必须同步；为什么中断不能随便在执行到一半的时候打断程序。以及最重要的，一个系统真正困难的地方，往往并不是把某个模块单独实现出来，而是把所有模块以正确的方式连接起来。这个项目没有追求实现一个功能庞大的处理器，目标相对克制：RV32I、Zicsr、异常与中断、AXI4-Lite、片上RAM、CLINT、UART、GPIO，再在此之上运行完整的C程序和一个最小实时系统。硬件规模并不大，但我希望整个系统是完整的。

## 本项目的推进时间线

- 4月，先写出一个RV32I单周期处理器。
- 5月，单周期版本很快证明只是一个起点，真正考虑可综合、可上FPGA的实现以后，原本简单的设计开始出现大量实际问题，于是进行了较大的重构，改成四阶段多周期结构，后来又改为五阶段，并尽量让接口和数据通路保留后续扩展成流水线的可能。
- 6月因为期末考试占用了主要精力，暂时停工，重新复习编译原理和并行计算，也让我意识到之前学过的很多知识在真正做系统的时候会重新以完全不同的形式出现。
- 7月，开始加入异常、CSR、中断以及总线，先后实现了Zicsr、ecall、ebreak、mret、异常处理以及时钟中断，并开始把CPU与外设连接起来。总线是一个很明显的分水岭，这一阶段也是整个项目中调试最痛苦但收获最大的部分之一。
- 8月，硬件终于开始像一台真正的计算机以后，接下来就是让它运行真正的软件，先是startup、C程序、ABI和内存布局，然后是UART驱动、shell、GPIO，最后实现了一个最小的实时系统，包括任务、上下文切换、调度、yield、延时、阻塞与唤醒以及基于CLINT的时钟tick，最终让多个任务真正运行在这个自己设计的处理器上。
- 9月，整理测试体系、补齐工程文档，并进行FPGA上的长时间压力测试。

## 写在一切结束之后

所以，如果这个项目最开始是为了证明，在AI面前，我们是否还剩下一些渺小而微薄的力量，我成功了吗？并没有。事实上，当我回顾这一切，感觉自己更像是挥剑劈砍风车的唐吉诃德。因为最终我得到的结论，恰恰不是人可以战胜AI，而是我们应该拥抱AI。没有AI的辅助，这个项目不可能在三个月左右、并且还是断断续续进行的情况下完成。很多时候，AI帮我写代码、解释协议、检查思路、寻找资料，它让实现本身的成本急剧下降。但与此同时，我也比以前更加清楚地看到了AI的边界在哪里。我现在越来越觉得，AI真正困难的地方，并不主要在于设计一个东西，也不完全在于把设计实现出来，它更像是在微笑曲线的两侧：需求，以及验证。

当我说我要做一个CPU的时候，这几乎没有任何意义。我要做什么ISA？支持哪些扩展？多少阶段？内存在哪里？系统使用什么总线？需要怎样的异常？软件需要运行到什么程度？RAM只有多少？这些问题不清楚，AI就无法真正替你完成设计。因为AI可以非常高效地提出一个实现，但它并不知道这个实现是不是我要的东西。这个项目一开始之所以不断重构，本质上就是需求不断被重新定义。从实现一个RV32I CPU，到实现一个可以综合、可以上板的多周期RV32I CPU，再到实现一个具有异常、中断、AXI、UART、CLINT，并可以运行C和实时系统的SoC，它们实际上是完全不同的需求。而越到后面，需求越具体。例如，最终的系统甚至有一些看起来极其琐碎的限制，指令和数据内存总和必须小于50KB。这个限制会直接影响RTOS应该实现什么，不应该实现什么。如果一个通用的消息队列系统吃掉了大量空间，那么我就必须思考，它是否真的值得存在；最终，与其实现一个缩水版FreeRTOS，不如把有限的资源用来实现一个真正运行的多任务应用。需求决定设计，而需求本身，恰恰很难自动生成。

另一个让我印象深刻的地方，是验证。AI可以帮我写出Verilog，却无法直接看到我FPGA仿真器里的波形，也无法凭空知道一个寄存器为什么在某一个时钟沿变成了某个值。它可以告诉我，这段逻辑看起来没有问题。但真正的问题可能藏在完全不同的地方。项目中就出现过这样的情况：反汇编完全正确，CPU的ALU结果也正确，某条指令单独测试也正确，但真正运行C程序时仍然会跑飞。最后发现的问题甚至不是CPU，而是ELF到binary的转换和内存布局。又或者，sw和lw单独测试完全通过，但C编译器生成的stack frame却出现了问题。这种bug很难靠读代码解决，最后还是必须回到波形、trace、内存内容、寄存器变化，以及真实硬件。人们总是倾向于相信自己愿意相信的东西。这当然不意味着人的检查天然比AI可靠，人同样会犯错，而且很多错误恰恰来自自信。但在很多验证成本非常高的场景里，验证本身就是一个独立的能力。芯片设计如此，机器人如此，任何真实世界系统都是如此。

我现在反而觉得，AI对计算机领域最大的冲击，很可能不是以后AI会不会写代码这么简单。Verilog前端没有那么高的壁垒，只要有一个足够好的接口，让AI能够真正获得waveform、仿真日志、综合结果，它就可以进行大量RTL设计和调试。底层软件也未必有那么高的壁垒，只要有明确的需求、明确的接口、清楚的硬件手册和足够完善的测试，AI同样可以完成大量底层工作。甚至计算机体系结构研究也是如此，很多体系结构研究最终形成的闭环其实非常简单，在一个受控的模拟器里，对多个设计方案进行性能、面积、功耗等trade-off，然后寻找更好的设计。只要需求明确，设计自动化本身就可能越来越容易。算子也是一样，真正困难的，可能不是把程序写出来，而是究竟应该做什么，以及怎么证明它做对了。这也意味着，一些今天看起来高度依赖写代码能力的领域，未来可能会发生非常深刻的变化，而需求和验证，反而可能成为越来越重要的能力。

这是我认真做的第一个数字IC或计算机体系结构项目，从目前来看，它也很有可能是最后一个，当然，我更希望它不是。至少这个项目让我重新确认了一件事情：我并不讨厌计算机，我只是越来越不满足于只是在别人定义好的问题里写代码。相比于把一个模型训练出来，我更喜欢知道一台机器为什么能跑起来；相比于把一个API调通，我更喜欢知道数据究竟经过了什么；相比于完成一个作业，我更喜欢自己定义一个目标，然后一路把它做出来。至于以后还会不会继续做CPU、数字IC或计算机体系结构，我不知道。作者之后可能会把更多精力投入机器人控制领域，在那里，真实世界会不断地给出反馈，自动化闭环更长，验证成本也更高，系统面对的不再只是一个受控模拟器，而是传感器、动力学、环境和现实世界本身。也许那里会有更高的挑战性，也有更多值得自动化、值得探索的东西。但不管以后走向哪里，这个项目至少完成了一件事情：它终于成为了一个真正属于自己的项目。从第一条RV32I指令，到最后FPGA上UART输出、GPIO闪烁、定时器中断、任务调度和应用程序真正运行起来的那一刻，中间没有一个现成的完成按钮，只能一层一层地做，一点一点地验证，然后，最终让它跑起来。
