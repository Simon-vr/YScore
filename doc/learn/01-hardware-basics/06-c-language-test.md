# 06. C Language Compilation Test

Once each class of assembly instruction passes, the next step is to verify that code generated by the C compiler runs correctly on this CPU.
This step completes the full toolchain of "cross-compile → ELF → memory file → on-board/simulation".

## 1. Toolchain

`rtos/CMakeLists.txt`:

- Compiler `riscv-none-elf-gcc`, `-march=rv32i_zicsr -mabi=ilp32 -mcmodel=medany`
  (`CMakeLists.txt:45-53`).
- `-O0 -g -ffreestanding -nostdlib -nostartfiles` (`CMakeLists.txt:56-64`):
  no libc, no default startup files, fully self-contained.
- Linker script `rtos/startup/link.ld` (`-T`, `CMakeLists.txt:66-71`).
- After generating the ELF, `ninja dasm` produces the disassembly, `ninja bin` extracts the `.text`/`.data` sections,
  and `ninja mem` calls `bin2mem.py` to generate the memory files (`CMakeLists.txt:121-166`).

## 2. Memory Layout (rtos/startup/link.ld)

```ld
MEMORY {
    irom (x)  : ORIGIN = 0x00000000, LENGTH = 18K
    dram (rw) : ORIGIN = 0x80000000, LENGTH = 24K
}
_sys_heap_size = 1K;
_sys_stack_size = 8K;
```

- `.text` goes into `irom` (starting at 0x0), and `_start` must be placed first (`*(.text.start)`).
- `.data` / `.bss` / `.stack` go into `dram` (starting at 0x80000000),
  `__global_pointer$ = ORIGIN(dram) + LENGTH(dram)/2`.
- `_stack_top = ORIGIN(dram) + LENGTH(dram)` (stack top = top of DRAM).

## 3. ELF → Memory File (bin2mem.py)

`rtos/bin2mem.py` performs two conversions:

1. **imem** (`convert_imem`): packs every 4 bytes of `.text.bin` into one 32-bit instruction in **little-endian**,
   one `%08x` per line. `core_if.v` reads it line by line with `$readmemh`.
2. **dmem** (`convert_dmem`): pads `.data.bin` up to 24KB,
   and splits it **byte-wise** into 4 bank files `dmem0.mem`~`dmem3.mem`,
   corresponding one-to-one with the 4 `mem_cell` blocks in `mem_ctl.v`.

Command-line usage (`CMakeLists.txt:159-166`):

```
python bin2mem.py 24 <text.bin> <data.bin> <output directory>
```

## 4. Test Program ins/test.c

`ins/test.c` is a "deterministic verification" program that comprehensively covers:

- Static `.data` array access (`checksum`, including XOR + addition).
- Stack `volatile mem[64]` writes + read-back verification (memory access).
- `logic_mix` (shift/XOR/add/sub, covering SLL/SRL/SRA/XOR/ADD/SUB).
- Signed branches (`if(a<b) ... else ...`) and unsigned branches (`if(a>b) ... else ...`).
- A large amount of mixed arithmetic.

The 30000-loop is to run for a few seconds on the FPGA (`test.c:45-51` comments).

**Deterministic verification idea** (`test.c:136-151` comments):
first run once on the host/simulator and record the expected value of `state`, then bake
`if(state != 0xXXXXXXXX) return 4;` into the test so the result is reproducible on the board.

## 5. Verification Method

1. Cross-compile `test.c` → generate `imem.mem`/`dmem0~3.mem`.
2. **Simulation**: run `sim.do`, look at the final `x31` in the tb snapshot (or the register corresponding to the program's `return` value).
3. **On board**: the `ins.bat` flow (assemble with `-march=rv32i_zicsr`, link with `-Ttext 0x0`,
   objcopy to produce bin, `bin2mem.py` to convert to mem), burn into the FPGA, and check the result register/GPIO.

## 6. Points Needing Special Attention for C Compilation

- **No standard library**: cannot rely on `memcpy`/`printf`; `rtos/sys/mem.c` provides `vPortMemCpy/Set`.
- **No multiply instructions**: `-march=rv32i` has no M extension; multiplication/division are inlined by the compiler to call
  the soft multiply/divide in `rtos/lib/math.c` (`umul/udiv/...`). Writing `i*17` in C also goes through soft multiplication.
- **Startup code**: there is no `crt0`; you must write your own `_start` to set up the stack, clear `.bss`, and set mtvec (see 02-software-stack/02).
- **Global pointer**: `__global_pointer$` is provided by the linker script, and `startup.S` does `la gp, __global_pointer$`.
